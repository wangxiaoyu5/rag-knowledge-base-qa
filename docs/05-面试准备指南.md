### 1.2 三分钟版本（详细版）

> **性能指标**：在 1000 份技术文档的测试集上，Recall@5 达到 85%，平均响应时间 500ms。

## 2. 核心技术问题

### 2.1 RAG 基础

**Q: 什么是 RAG？为什么需要 RAG？**

**A:** 
- **定义**：RAG（Retrieval-Augmented Generation）是将信息检索与文本生成结合的技术
- **核心思想**：先从知识库检索相关信息，再基于检索结果生成答案
- **解决的问题**：
  1. LLM 幻觉问题：基于真实文档生成，减少编造
  2. 知识时效性：无需重新训练即可更新知识
  3. 可解释性：答案可溯源到原始文档
  4. 成本：比微调大模型成本低得多

**Q: RAG 和 Fine-tuning 的区别？**

**A:**

| 维度 | RAG | Fine-tuning |
|------|-----|-------------|
| 知识更新 | 实时更新文档即可 | 需要重新训练 |
| 成本 | 低（只需存储和检索） | 高（训练资源） |
| 幻觉 | 低（基于真实文档） | 仍可能产生 |
| 可解释性 | 高（可追溯来源） | 低（黑盒） |
| 适用场景 | 知识库问答、客服 | 特定风格/格式 |

### 2.2 检索技术

**Q: 向量检索和关键词检索的区别？**

**A:**
- **向量检索**：
  - 原理：将文本转为向量，计算余弦相似度
  - 优点：理解语义，支持同义词、近义词
  - 缺点：对关键词匹配不精确，计算成本高
  
- **关键词检索（BM25）**：
  - 原理：基于词频和逆文档频率计算相关性
  - 优点：精确匹配关键词，速度快
  - 缺点：无法理解语义，需要完全匹配

**Q: 什么是 RRF 融合算法？**

**A:**
```
RRF (Reciprocal Rank Fusion)
公式：score = Σ(1 / (k + rank_i))

其中：
- k: 常数（通常60），控制低排名的影响
- rank_i: 文档在第i个结果列表中的排名

示例：
文档A在向量检索排第2，在BM25排第5
文档B在向量检索排第5，在BM25排第2

k=60时：
文档A得分 = 1/(60+2) + 1/(60+5) = 0.0161 + 0.0154 = 0.0315
文档B得分 = 1/(60+5) + 1/(60+2) = 0.0154 + 0.0161 = 0.0315

如果文档A在BM25排第1：
文档A得分 = 1/62 + 1/61 = 0.0328（更高）
```

**Q: Cross-Encoder 和 Bi-Encoder 的区别？**

**A:**

| 特性 | Bi-Encoder | Cross-Encoder |
|------|------------|---------------|
| 架构 | 两个独立编码器 | 单个编码器 |
| 输入 | 分别编码查询和文档 | 拼接查询和文档一起编码 |
| 速度 | 快（可预计算） | 慢（需实时计算） |
| 精度 | 较低 | 较高 |
| 适用阶段 | 粗排（召回） | 精排（重排序） |

**Q: 如何评估检索效果？**

**A:**
- **Recall@K**：前K个结果中相关文档的比例
- **Precision@K**：前K个结果中相关文档的准确率
- **MRR (Mean Reciprocal Rank)**：平均倒数排名
- **NDCG**：考虑相关度等级的指标

### 2.4 文本分块

**Q: 文本分块有哪些策略？如何选择？**

**A:**

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 固定字符 | 按固定长度切分 | 简单 | 可能切断句子 |
| 递归分块 | 按优先级尝试分隔符 | 保持语义 | 块大小不均 |
| Token 分块 | 按 Token 数切分 | 精确控制 | 需要 Tokenizer |
| 语义分块 | 按语义边界切分 | 语义连贯 | 计算成本高 |

**选择建议**：
- 通用场景：递归分块
- 严格长度限制：Token 分块
- 高精度要求：语义分块

**Q: chunk_size 和 chunk_overlap 如何设置？**

**A:**
- **chunk_size**：
  - 太小（<200）：上下文不足，检索精度低
  - 太大（>1000）：噪声多，检索精度低
  - 推荐：300-800，根据文档类型调整

- **chunk_overlap**：
  - 作用：保持块间上下文连贯
  - 推荐：chunk_size 的 10%
  - 示例：chunk_size=500，overlap=50

## 4. 场景题与优化

### 4.1 场景题

**Q: 如果检索结果不准确，如何优化？**

**A:**
1. **Query 优化**：
   - Query Expansion：扩展同义词
   - Query Rewrite：重写查询
   - HyDE：生成假设文档再检索

2. **检索策略优化**：
   - 调整混合检索权重
   - 优化重排序模型
   - 多路召回（向量+关键词+图谱）

3. **数据优化**：
   - 优化分块策略
   - 添加更多元数据
   - 数据清洗和增强

**Q: 如何处理多轮对话？**

**A:**
```
方案1：简单拼接
- 将历史对话拼接到当前 Query
- 优点：简单
- 缺点：上下文过长

方案2：历史摘要
- 用 LLM 总结历史对话
- 优点：减少长度
- 缺点：可能丢失信息

方案3：独立检索+综合
- 每轮独立检索
- 最后综合所有结果
- 优点：信息完整
- 缺点：成本高

推荐：方案2+方案3结合
```

**Q: 如何支持实时更新的知识？**

**A:**
1. **增量更新**：
   - 只更新变化的文档
   - 删除旧向量，添加新向量

2. **定时任务**：
   - 定时扫描文档变化
   - 批量更新向量库

3. **实时监听**：
   - 监听文件系统变化
   - 实时更新向量库

### 4.2 优化案例

**案例1：检索精度低**

```
问题：用户反馈检索结果不相关

分析：
1. 检查 Query 和文档的 Embedding 相似度

优化：
1. 使用领域特定的 Embedding 模型
```

**Q: 如何实现一个新的文档加载器？**

**A:**
```python
from core.document_loader import BaseDocumentLoader
from langchain.schema import Document

class ExcelLoader(BaseDocumentLoader):
    def load(self, file_path: str) -> List[Document]:
        import pandas as pd
        df = pd.read_excel(file_path)
        
        # 每个 Sheet 作为一个文档
        documents = []
        for sheet_name in df.sheet_names:
            sheet_df = pd.read_excel(file_path, sheet_name=sheet_name)
            text = sheet_df.to_string()
            documents.append(Document(
                page_content=text,
                metadata={
                    "source": file_path,
                    "sheet": sheet_name,
                    "file_type": "excel"
                }
            ))
        return documents
    
    def supports(self, file_extension: str) -> bool:
        return file_extension.lower() in ['.xlsx', '.xls']

# 注册
DocumentLoaderFactory._loaders.append(ExcelLoader())
```
